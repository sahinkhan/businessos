# ADR-022: Module-Scoped Database Execution Authority

Status: PROPOSED

Decision date: Pending formal acceptance.

Approving roles required: Architecture Maintainer; Platform/Kernel Maintainer; Security Maintainer; Migration Safety Reviewer; Release Maintainer; Data Governance Owning Domain Maintainer; SDK/Contract Maintainer; Audit Owning Domain Maintainer; affected participating Resource Owning Domain Maintainer

Approval pull request or commit: Pending proposal review.

Supersedes: None

Superseded by: None

## Context and threat model

The independent audit of the [ADR-017 implementation candidate, PR #45](https://github.com/sahinkhan/businessos/pull/45) found a blocking Medium: a handler using the shared `businessos_app` PostgreSQL principal can directly update a same-tenant `platform_gov.legal_holds_v2` row. It can bypass the Governance command, subject and policy locks, owner validation, Audit append, and outbox transaction. [ADR-017](ADR-017-retention-hold-and-purge-coordination.md) requires those operations to be one authority path. PR #45 remains draft, blocked, and unchanged by this proposal; its passing CI and application-level checks do not certify the SQL boundary.

The current runtime has one ordinary application engine and session factory. The dispatcher captures an `_OwnedHandler` and admits its exact `ContributionGeneration`, then creates a tenant-scoped Unit of Work (UOW) from that shared factory. [ADR-020](ADR-020-trusted-handler-invocation-authority.md) issues a protected `HandlerInvocationBinding` inside that transaction for application-level authority. PostgreSQL sees `businessos_app` for Governance and other modules alike. Forced row-level security (RLS) proves tenant scope but cannot prove which BusinessOS handler issued a same-tenant statement. A valid tenant GUC therefore does not close this finding.

The protected asset is the meaning and evidence of destructive authority, not only one table. The PR #45 candidate creates `platform_gov.retention_policies_v2`, `legal_holds_v2`, and `destructive_decisions_v2` with tenant RLS but grants `businessos_app` `SELECT, INSERT, UPDATE`. Existing `gov_0002` grants that role broad DML on older Governance tables, including `platform_gov.legal_holds`. V2 conservatively treats active legacy holds as blockers, so deactivating a legacy hold can also bypass the V2 lock path. A policy duration, effective interval, action, active flag, hold state, decision row, or cleanup status can weaken protection or falsify evidence. Historical or future tables, views, functions, sequences, triggers, and inherited privileges that can change any such state are in the same authority inventory. Legacy `retention_policies` are currently rejected by the V2 migration preflight rather than used as V2 policy authority; they remain subject to a compatibility inventory, not an assumption that legacy writes are harmless.

The adversary is an ordinary module handler, worker path, tenant caller, or compromised same-tenant application code with the normal SQL session and its public dependencies. The target guarantee is that this SQL principal cannot mutate Governance destructive authority or acquire its role. The separate first-party credential is protected from SDK and module injection. This is not an in-process sandbox against arbitrary code executing with full operating-system access to the server process or its memory; executable customer and marketplace modules retain the isolation required by [MODULES.md](../architecture/MODULES.md). A compromise of trusted first-party Governance code or of its protected credential remains a high-trust incident and requires operational containment.

## Decision

### Protected execution identity and selection

Introduce a bounded, protected module-scoped database execution role and connection pool for approved sensitive first-party command handlers. The initial mapping is selected `foundation.data_governance` command registrations to `businessos_governance`; ordinary handlers continue to use `businessos_app`. It is a protected runtime mapping of approved owner, exact command registration/handler identity, handler kind, and current generation to an execution profile. It is **not** a generic ability for a module to request a role. Privileged queries or other handlers need a separate reviewed entry; they do not inherit the role merely because they share a module ID.

The dispatcher must capture the exact `_OwnedHandler`, admit that generation through the existing `ContributionGate`, and verify trusted `ModuleRegistration` provenance tied to the verified, operator-approved first-party `ApprovedModuleArtifact` and loaded module before the protected UOW factory chooses a pool. The active protected mapping and captured handler/generation must still match at acquisition. Direct/low-level `HandlerRegistry` registrations, unapproved artifacts, manifest claims alone, stale generations, wrong handler kinds, and missing provenance use no privileged pool and fail closed if the command requires it. Request fields, payloads, tenant configuration, environment values supplied by a module, provider names, permission strings, and caller-supplied `module_id` never select the role. The protected mapping and credential are installed by trusted composition/operator configuration, outside module manifests and ordinary dependency injection.

This selection uses the same protected provenance inputs as ADR-020, but it cannot depend on the `HandlerInvocationBinding` object: that binding is issued after the UOW starts. Inside the selected transaction the framework still issues and validates the ADR-020 binding against the same exact admitted handler, generation, request, transaction, task, and lease. Database role and application binding are both required; neither substitutes for the other. A generation admitted before drain may finish on its already admitted transaction; after drain begins no new admission or privileged transaction is issued. Replacement generation B needs fresh approval and mapping. A stale generation cannot start a new privileged UOW, even if a pooled connection exists.

### PostgreSQL role and grant boundary

`businessos_governance` is a distinct `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS` runtime principal, not a schema/table owner, migrator, operations role, or universal module superuser. It receives explicitly enumerated ordinary baseline privileges needed by a Governance transaction, plus reviewed DML on protected Governance authority tables and narrow participating-owner operations. Grants are table/operation specific; no `ALL TABLES` or default future grants to this role. It does not inherit `businessos_app`: the older broad app grants would otherwise expand its authority. Membership direction and `INHERIT` options must be audited. Neither `businessos_app` nor `businessos_worker` may be a member of, inherit from, or `SET ROLE` to `businessos_governance`; the existing worker-to-app membership must not create an indirect path. Governance cannot become `businessos_migrator` or `businessos_ops`. The migrator retains reviewed DDL/seed authority; ops retains its separate operational purpose and is never the ordinary command connection.

On protected Governance authority tables, `businessos_app` and `businessos_worker` get only necessary tenant-scoped reads and **no** direct `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, ownership, or indirect write path. `businessos_governance` gets only the DML each admitted Governance command requires. An implementation must inventory and revoke ordinary write privileges on all V2 policy, hold, decision, and cleanup-evidence state and on authoritative legacy holds, including inherited grants, routines, writable views, sequences, and default privileges. It must also prove whether any older policy or other Governance row remains an input to V2 decisions; if so, protect it before certification. An ordinary actor may still request an authorized Governance command, but cannot execute its SQL or bypass its locks and evidence through a normal app connection.

PostgreSQL RLS remains an independent condition: every tenant-owned table touched by the transaction, including Governance, Audit, Eventing, Policy/Identity reads where needed, and participating-owner tables, uses enabled and forced RLS with a reviewed policy for `businessos_governance`, constrained by the trusted `SET LOCAL app.tenant_id` in the active transaction. Existing policies scoped `TO businessos_app` do not automatically cover a separate Governance role; explicit role policies and grants are required before use. That role has `NOBYPASSRLS`; a missing, malformed, or mismatched tenant denies. The role does not gain cross-tenant visibility. Global canonical tables remain governed by their separate accepted grant models. A PostgreSQL GUC for module identity is never used as role proof because an app session can set it itself. `SET ROLE` is forbidden by membership design, not treated as a protected selection mechanism. A `SECURITY DEFINER` routine callable by all app sessions is likewise insufficient without separate authenticated authority.

### One UOW and cross-module owner operation

The protected factory chooses the Governance engine **before** creating the single tenant UOW. That one PostgreSQL connection and transaction execute Governance policy/hold/decision SQL, [Audit V2](../architecture/AUDIT-V2-RUNTIME-IMPLEMENTATION.md) append, the [ADR-018](ADR-018-canonical-resource-ownership-and-owner-operation-boundary.md) admitted owner provider's validation/apply, and transactional outbox insert. The restricted `HandlerTransaction` is passed to the provider; no second transaction, autonomous commit, role switch, or privileged session is handed to it. Any failure rolls back all effects. The existing tenant GUC, lock ordering, and cleanup rules remain mandatory.

An owner adoption must explicitly review the exact owner operation and grant the Governance execution role only the owner-table privileges it needs in the same UOW, with tenant RLS and owner-side constraints still enforced. Audit owns its append table and must explicitly grant its required append privilege to the Governance role; Eventing owns outbox grants. Reads of Policy and Identity needed for authorization are separately inventoried. This role-level ability is **not** resource ownership: Governance code still cannot directly update an owner's private table as a contract matter, and the admitted ADR-018 owner provider must validate facts, capability, lock order, and mutation. Because the same SQL principal is used within one transaction, PostgreSQL cannot distinguish Governance coordinator SQL from owner-provider SQL; the database grants bound the maximum damage, while first-party code review and the ADR-018 application contract enforce which component uses them. A table whose required grant is too broad for that trust model must use a separately reviewed narrow owner-owned operation mechanism in the same transaction or remain unenrolled. No owner is silently enrolled and no superuser/BYPASSRLS shortcut is allowed.

The role is an execution identity, not a workload identity. [ADR-019](ADR-019-trusted-workload-identity-and-worker-execution.md) still authenticates worker origin and permissions. `businessos_worker` does not inherit Governance DML. An approved worker request may dispatch a Governance-owned command, and the exact admitted command handler, not worker-supplied identity or a generic worker event handler, determines the pool. Direct event/job SQL and untrusted worker registration get no Governance role.

### Pool and lifecycle

Protected runtime composition owns a distinct bounded Governance engine/session factory with its own secret reference. The credential, engine, pool, and unrestricted session are not exposed through the SDK, `RequestDependencyScope`, module manifest, tenant configuration, provider registry, or ordinary DI. UOW creation verifies the selected connection's expected database and SQL role; mismatch or unavailable credential denies the privileged command and never falls back to `businessos_app`, `businessos_ops`, or a second UOW. A normal command can only acquire the normal pool. Pool sizing and idle limits are configured per installation with a small bounded default and connection-budget check; the number of profiles grows only with explicitly approved sensitive modules, never with tenants.

Connections are returned only after commit/rollback and close, including cancellation/error paths. Tenant identity uses transaction-local `SET LOCAL`; on transaction end it cannot persist to the next borrower. The implementation must reset/discard session-level role, GUC, search-path, prepared/session state and verify no privilege or tenant leakage on reuse. It must never run `SET ROLE` as ordinary pool multiplexing. Pool shutdown drains admitted work and disposes connections. Credential rotation creates a new protected pool from a rotated secret, validates its identity and grants, stops new admissions on the old pool, lets admitted transactions finish or rolls them back on deadline, and disposes old connections. Rotation failure denies privileged commands; it does not weaken authority or disclose the secret. Health/readiness reports privileged-path unavailability without credential contents. Audit logs record selected protected profile and exact handler generation without treating log metadata as authorization.

### Provisioning, upgrade, and failure semantics

Fresh installations create the role through reviewed database bootstrap/provisioning before any migration grants to it. Existing installations need an idempotent, separately credentialed operator role-provisioning step before the forward Governance migration; a Docker init script alone cannot update an existing PostgreSQL volume. The future migration must verify the role's attributes, membership closure, database target, and required policy/grant prerequisites before applying grants or revoking old ones. The subsequent runtime release supplies the separate protected secret/pool and exact handler mapping. A staged upgrade may first provision and validate the role, then deploy protected runtime, then atomically narrow ordinary grants with the forward migration; destructive Governance commands remain disabled until all three agree. There is no interval in which a newly enabled command relies on a still-writable shared role. If an installed client or V1 hold command cannot use the protected path, its weakening mutation is disabled with explicit compatibility/release handling until routed through the protected Governance command; legacy authoritative holds cannot be directly deactivated by `businessos_app`.

Future implementation is expected to touch database role bootstrap and production provisioning, secret/config examples, Compose/test wiring, UOW factory and dispatcher composition, protected mapping, Governance/Audit/Eventing/participating-owner grants and RLS, and migration smoke tooling. This proposal changes none of them. Historical migrations are immutable; grant correction is forward-only and must be safe for fresh install, existing-volume upgrade, restore, and replay. Self-hosted deployments need PostgreSQL credentials and bounded pools only; no Kubernetes, service mesh, or per-tenant database role/pool is required. Startup fails closed for protected commands if provisioning or privilege inspection fails, while unrelated ordinary commands may remain available when safe. A failed migration or incompatible grant state blocks ADR-017 certification and gives operators a repair path without silently reverting to shared-role DML.

## Alternatives considered

| Option | Assessment |
| --- | --- |
| A. Shared `businessos_app` plus tenant RLS | Rejected: RLS distinguishes tenant rows, not admitted module handlers; same-tenant direct SQL remains possible. |
| B. Shared role plus `app.module_id` GUC | Rejected as sole authority: `businessos_app` can set a custom GUC and impersonate a module. RequestContext, Python stack, dependency names, SQL comments, `application_name`, and correlation IDs are likewise not database-authenticated role proof. |
| C. Shared role plus `SET ROLE` membership | Rejected: if app or worker can assume Governance's role, arbitrary SQL in that session can do so. Protected pool identity needs no role switch. |
| D. `SECURITY DEFINER` mutation procedures | Rejected as sole authority when every app caller can invoke a weakening routine. A narrowly reviewed owner-owned routine may support a specific cross-module owner operation only with safe ownership, fixed `search_path`, grants, RLS behavior, parameters, and error disclosure. |
| E. Protected module-scoped role and pool | Chosen: PostgreSQL distinguishes the execution principal, the dispatcher selects it from verified exact handler provenance, and one UOW still spans the ADR-017 operation. It adds bounded pools and operational provisioning without per-tenant role growth. |
| F. Per-module service/database | Not required for this first-party modular-monolith boundary. It would make the atomic Governance/Audit/owner/outbox transaction and self-hosted operations substantially harder; revisit only with measured isolation or scale reasons. |
| G. Application-only SQL interception | Rejected as sole authority: raw SQL, SQLAlchemy Core, or a missed path can bypass interception under the same database principal. |

## Compatibility, consequences, and implementation gates

This decision adds a protected kernel/persistence trust boundary. Affected owners include Platform/Kernel, Data Governance, Audit, Eventing, and each resource owner adopting destructive operations. Policy and Identity read/grant behavior must be inventoried; their domain ownership and public contracts do not change merely because a Governance transaction uses a different role. The current `UnitOfWorkFactory`/handler transaction surface should remain source compatible for ordinary modules; any necessary public SDK or contract change requires SDK/Contract Maintainer approval, versioning, and conformance tests. No module receives a public role-selection API. Existing tenant scopes, database-per-tenant and shared-schema deployments, and dedicated self-hosted installation remain supported. Phases 0–3 remain FINAL PASS / FROZEN with no general reopening.

Before ADR-017 implementation certification, the accepted ADR-022 runtime and forward database changes must prove with real PostgreSQL: app and worker direct UPDATE/DELETE of V2 and legacy holds denied; app weakening of policy and falsification of decision/cleanup evidence denied; app/worker `SET ROLE businessos_governance` denied, including indirect membership; trusted exact-generation Governance command DML succeeds; unapproved/direct/stale registrations fail closed; cross-tenant Governance-role DML denied by forced RLS; same-UOW owner, Audit, decision, and outbox commit or roll back together; provider lock order and generation drain remain correct; connection reuse, rotation, cancellation, startup failure, and restored-volume upgrade leak no tenant or role authority. The grant inventory must include all indirectly writable authority state, sequences, functions, views, owner operations, and future defaults. Conformance must run against fresh and upgraded databases and preserve ordinary app and worker functionality.

ADR-022 acceptance is architecture authority only, not an implementation certificate. PR #45 must remain draft and blocked at candidate `c2d89ce5841a0a3b186b3483baba3f6c6f8a58b9` with its existing Critical 0, High 0, Medium 1, Low 0 audit until the new boundary is implemented, certified, and merged. Afterward PR #45 must be rebased or recreated from new main, so its current SHA and CI are obsolete; it needs fresh PostgreSQL security proofs, exact-head CI, independent audit, and owner review. ADR-021 remains reserved for V1 Runtime Elimination. This proposal neither performs that work nor weakens the accepted [ADR-018](ADR-018-canonical-resource-ownership-and-owner-operation-boundary.md), ADR-019, or ADR-020 boundaries.
